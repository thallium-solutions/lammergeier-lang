# Lammergeier benchmarks

Two suites, measuring different things. They are not tests: nothing fails
on a slow number; they produce numbers to compare over time and between
machines (`--json` for raw results).

| Suite | Question | Runner |
|---|---|---|
| `compiler/` | How fast does `lamc` compile, phase by phase? | `sh scripts/bench.sh compiler` |
| `runtime/` | How fast is the Go code `lamc` generates, compared with hand-written Go? | `sh scripts/bench.sh runtime` |

## Compiler (`benchmarks/compiler/`)

`run_compiler_bench.py` builds every program with `lamc build --timings`
(available to everyone: it prints one `LAMC_TIMINGS {...}` JSON line with
milliseconds per phase) and reports medians:

| Phase | Meaning |
|---|---|
| `preprocess` | semicolon insertion, `go!` extraction, aliases (all modules) |
| `parse` | Lark parsing (all modules) |
| `semantic` | the semantic checker |
| `transpile` | Lam AST to Go (main program and libraries not in the cache) |
| `go_mod`, `go_build` | `go mod init/tidy`, `go build` |
| `other` | everything else (module resolution, namespacing, I/O) |

The corpus: programs generated by `gen_program.py` in three sizes (about
350, 3,500 and 14,000 lines, identical everywhere), the programs in
`corpus/`, and any `--project main.lam` (with `--extlibs`), e.g. a real
application. `--mode cold|warm|both` (library cache off or primed),
`--front-end` skips `go build` to isolate the Python compiler, `--runs N`.

```bash
sh scripts/bench.sh compiler --front-end
sh scripts/bench.sh compiler --project ~/code/app/main.lam --extlibs ~/code/app/extlibs --extlibs ~/code/app/lib
```

## Runtime (`benchmarks/runtime/`)

Each `cases/<group>/bench_<name>.lam` declares `# ops: N`, runs its workload
in `work()` and times only that workload (no process start, Go runtime init
or imports), printing `BENCH <name> <ops> <elapsed_ns>`. The runner builds
each program once, runs it `--runs` times (default 5) and reports the median
and best time, the time per operation and the spread (median absolute
deviation). A hand-written `bench_<name>.go` next to a benchmark is the
baseline: the `lam/go` column (and the geometric mean) is the overhead of
the generated code.

```bash
sh scripts/bench.sh runtime
sh scripts/bench.sh runtime -f json --runs 9 --json out/runtime.json
```

Groups: `language/` (calls, loops, lists, list indexing with a runtime
index, dicts, strings, dispatch, f-strings) and `stdlib/` (JSON, regex, hashing, sorting, splitting).

## Results

`scripts/bench.sh` prints the report and writes it, with a header (version,
commit, date, command, CPU, load average, Go version), to
`benchmarks/results/<suite>-<UTC time>-<version>-<commit>.txt`. Commit the
file with the change it measures, so numbers can be compared across
releases; `BENCH_SAVE=0` only prints.

## Adding a benchmark

- Runtime: copy an existing `bench_*.lam`, keep `# ops:` accurate, size the
  workload to 10-200 ms, consume the result so Go cannot remove the loop,
  and say in the header comment what it stresses. Add a `bench_*.go` with
  the same workload and output when a baseline makes sense.
- Compiler: drop a representative, self-contained program in `corpus/`.

Run the suites on an idle machine; compare medians of several runs.
